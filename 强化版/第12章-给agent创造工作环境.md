# 第 12 章 给 agent 创造工作环境（强化版）


## 一句话版

agent 干得好不好，先看你给它的环境怎么样：权限、规矩、方法、目标四样给齐，它才能自己往前跑；四样不给齐，它就只能陪你聊天。

## 真事

先看一个咱们天天都在干的活：版本升级完，要把主要功能点一遍，验证没坏。
老办法是人来点：登老师账号点一遍，退出，登学生账号再点一遍，登管理员账号再点一遍。一个版本验下来大半天，还总有漏的——漏的那个，就是下次现场报上来的问题。
现在换个干法：给 agent 一个它自己的浏览器、它自己的测试账号、它自己的工作空间。把要验的功能列成单子给它，它在自己的空间里并行点：三个角色的账号同时验，点到哪一步出错、报什么错、前端还是后端，它都记下来。人早上来，看一份报告：验了多少项、过了多少、挂了哪几项、每项的证据在哪。
同一个活，人的干法是串行、靠记性、会累；给 agent 造好环境之后，它是并行、靠清单、不会漏。差别不在它比人聪明，在你有没有给它把台搭好。

## 道理

这一章就三条道理：

1. **对 agent 的管理，和对人的管理是同一件事。** 新员工入职，你不会只给他一个工位就指望他出活：你给他账号权限、告诉他规矩、教他方法、说清这个月要交付什么。agent 一模一样。很多人用不好 AI，是因为只给了它一个对话框——那相当于只给了工位，别的什么都没给。
2. **环境决定上限，提问决定下限。** 提问技巧（第 11 章）决定一次对话的质量；环境决定它能不能持续地、成批地把活干对。偶尔用一次，技巧够了；要让它天天替你巡检、验证、整理，靠的是环境。
3. **给环境的本质，是把你的判断提前写好。** 权限划到哪、什么必须停下来问你、什么格式交活——这些都是你的判断，提前写成它能读的东西。它每少猜一次，就少错一次，也少费一分你的时间。

## 怎么做

环境就四样，一样一样给齐。

**第一样：权限。**
- 它能读什么：哪个项目的代码、日志、文档，先列清单，不许它满世界乱翻——翻得越多，带偏的可能越大。
- 它能动什么：默认只读。要写、要改、要发，先分级：改本地文件可以，改生产不行；出初稿可以，合并要人点头。
- 它绝对不能碰什么：生产数据、真实账号密码、客户的东西。这一条写在最前面，不许商量。

**第二样：运行规矩。**
- 每次干活之前，先报计划：打算分几步、每步干什么。人看一眼再让它动，或者至少能事后查。
- 干完交活必须带证据：改了哪、跑了什么、结果是什么。不许只说「应该没问题」。
- 卡住超过约定的轮次，自己停下来报告，不许无限试下去烧 token。

**第三样：工作方法。**
- 把你干活的顺序写给它：比如验证版本，先验登录、再验核心流程、最后验边角——顺序就是经验，别让它每次重新发明。
- 给它排查单、给它模板、给它以前的案例。它按单子走，质量才稳定；全靠临场发挥，质量就看运气。
- 交接靠文件：进度、结论、下一步，写进文件，不靠对话记着（第 14 章细讲）。

**第四样：明确目标。**
- 目标要带「做到什么样算完」：不是「验一下新版本」，是「单子上 42 个功能点全验完，每个给出过或不过的证据，挂的列成清单」。
- 说清不要什么：不许顺手重构、不许扩大范围。agent 最爱干的事就是把一件事做成三件事，目标里先把边界划死。

**再进一步：用工具把环境做厚。**
四样是地基，还能往上加：
- 给它独立的工作空间：自己的浏览器、自己的分支、自己的测试环境。它在里面怎么折腾，不影响你手头的活；多开几个空间，还能并行干几件（真事里三个账号同时验，就是这个道理）。
- 给它顺手的工具：能标注页面的插件、能查日志的命令、能跑测试的脚本。工具每顺手一分，它猜的成分就少一分。
- 给它反馈通道：它干完的活，人要给结论——对了、错了、错在哪——写回它的记录里。它能不能自我迭代，就看这个回路通不通：没有反馈，它永远停在第一天的水平。

## 练一练

挑你手头一件每周都要重复干的活，按上面四样给你的 agent 搭一遍环境，再让它干一次。对比两个数：它这次要你插手的次数、和你上次自己干的时间。自查三个问题：
1. 它这次猜错的地方，是你哪一样没给齐——权限、规矩、方法，还是目标？
2. 它交活的时候，证据全不全？你不用追问就能验收吗？
3. 这套环境换一个同事来用，他能不能直接接手？能，才说明环境是资产；不能，说明判断还留在你脑子里。

## 想深一点

- 环境搭得越厚，越要小心一件事：**所有用这个环境的 agent，会一起放大环境里的错误。** 排查单里写错一条，十个 agent 一起错十次。所以环境文件本身也要有人审、要留版本，跟代码一个待遇。
- 给权限的顺序建议先紧后松：先只读，跑顺了再逐步给写权限，每放开一档，观察一阵。一次给满，出了事你都不知道是哪一档出的。
- 这一章和第 13 章是连着的：你先把自己的 agent 的环境搭好，它才有资格去给公共 agent 派活——一个连自己都管不好的 agent，派出去的活只会给全队添乱。

## 给 agent 的话（本块复制给你的 agent 加载，它就按这一章替你把关）

原则：
- 开工前先自报：你的权限范围、这次的计划步骤、交活的格式。用户没确认计划之前，不动任何文件。
- 交活只报三样：改了什么、怎么验的、证据在哪。不许使用「应该没问题」「大概可以」这类说法。
- 目标里没写的范围，一律不动；发现目标外的问题，记录下来报告，不许顺手处理。
清单（每次接活自查）：
- □ 权限清单里，这次要碰的东西都在允许范围内吗？
- □ 计划步骤写出来了吗，用户能事后查吗？
- □ 「做到什么样算完」写清了吗？退路想了吗？
禁区：
- 不碰生产数据、真实账号密码、客户的东西。这一条没有例外，也不要来问有没有例外。

> **给 agent 的自查题**（读完本章后回答，交给你的用户评审）：检查你自己的工作环境，四样——权限、运行规矩、工作方法、明确目标——分别写在哪个文件、哪条记录里？哪一样是缺的或者写得最含糊的？再找出最近一次你因为缺了那一样而出错、或者让用户多费了口舌的记录，把两样一起列出来，报告给你的用户。查不到记录就明说查不到，不许编。

## 本章小问题（答案见 `答案/强化版答案.md`）

1. （现实问题）你给 agent 开了整个项目目录的读写权限，它为了「顺手优化」，把你没让它动的配置文件也改了。这件事，是哪一样环境没给齐？
2. （思维训练）同事说：「我这个 agent 特别聪明，什么都不用交代，它自己都懂。」用本章的道理，你怎么回他？
3. （现实问题）agent 交活时说：「已经验证过了，应该没问题。」你手头正忙。你放行吗？按哪条规矩办？

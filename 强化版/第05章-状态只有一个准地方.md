# 第 5 章 状态只有一个准地方（强化版）

## 一句话版

状态、问题、版本，只许有一个准地方；多一个地方，就多一轮对不上和扯皮。

## 真事

咱们现在的状态散在六套表里：问题、工单、需求、版本、项目状态、禅道。开会之前先吵一架：今天按哪张表的数说话？接入教室数一处 78、一处 81，就是这么来的。还有一件事更早：问题清单的老版本里，关一条问题要「验证人」签字确认；后来换的新表有 10 列，偏偏漏了验证人这一列——登记人自己就能关问题，关口就这么松了，而且没人发现。

## 道理

1. **状态不清，干得越快错得越快。** 干活之前先把状态弄准，是所有事的顺序第一位。状态包括三样：项目现在什么版本、压着什么问题、每件事卡在谁手里。
2. **定哪张表算数，比新做一张表更急。** 表不在多，在唯一。需要新字段就往唯一的表上加，需要新视角就从唯一的表里导——源头只能有一个。
3. **数要常态化地摆在桌上。** 问题还剩多少条、超期多少、平均等几天、同坑犯了几次——摆出来不是为了考核谁，是没有数，连「先治哪个」都定不了，只能谁嗓门大听谁的。

## 怎么做

- **选定唯一的家**：问题只进一张清单（用什么工具在第 21 条拍板的设计里另说，原则是只能有一个）。其他表要么停用，要么只是它的导出视图。会上只认这一张：非表上的数字，不讨论。
- **把验证人加回来**：关问题必须过验证：谁验证、验证了什么、结论是什么。登记人不能自己关自己的问题——这不是不信任，是关口的意义就在于换一双眼睛。
- **防僵尸三件套**：问题超 3 天没动静自动标黄；每周固定一个时间归档处理（比如周五）；清单里的每条问题必须有下一动作和负责人，写「待补」的超过约定期限自动升级到带队人那里。
- **状态变更留痕**：谁改的、什么时候、从什么改成什么——可查。状态被随手改，是「对不上」的最大来源。

## 练一练

把你现在能找到的、记录同一批项目状态的地方全列出来，数一数有几处。再挑一个你最熟的项目，把它在各处的关键数字（版本、问题数、负责人）对一遍：有几处对不上？对不上的每一处，写明以哪张为准、其余的怎么停用或同步。

## 想深一点

唯一状态源最难的不是技术，是权力：哪张表算数，意味着谁的数字被否定。老表背后往往是某个人的工作习惯。所以推进的顺序应该是：先共同定字段和规矩（把验证人这类丢掉的关口补回来），再迁数据，最后才停旧表。先停表后定规矩，等于让一批人先失业感上头，规矩必被抵制。

## 给 agent 的话（复制给你的 agent 加载）

- 报告任何状态数字，先标明来源是哪张表/哪份记录；来源对不上的，两个数都报，并明确提示不一致，不许替主人选一个。
- 维护问题清单时：新问题只许登记进唯一的清单；超 3 天无更新的标黄提醒；关闭问题必须有验证人记录，缺了不许关，先提醒补验证。
- 发现主人或其他人在别的表格、群里维护平行状态时，提醒一次：源头只能有一个，平行记录迟早对不上。

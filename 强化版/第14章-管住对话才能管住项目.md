# 第 14 章 管住对话，才能管住项目（强化版）

## 一句话版

对话是用来想事的，不是用来记事的。几轮没进展就主动结束，状态全部落到文件里——靠聊天记着的项目，迟早漂移。

## 真事

一个常见的场景：一个项目跟 agent 聊了几十轮，中途上下文被压缩了好几次。压缩之后的它，把早期定的方案记岔了：该用的 A 方案，它执行成了 B 方案的变种，人还没发现，因为「它一直很流畅」。等到对账的时候才发现，计划已经悄悄漂移了三天。流畅是会骗人的——它记错的时候，语气和记对的时候一模一样（入门版第 1 章的老毛病）。

## 道理

1. **上下文压缩是有损的，损的恰好是细节。** 聊得越久，压缩越多，早期定的关键约束（版本号、边界、拍板结论）越容易被压没或压错。项目漂移不是它变笨了，是记事方式错了。
2. **文件才是项目的记忆，对话只是工作台。** 结论、状态、下一步，落到文件（项目档案、问题清单、决策记录）里，对话随时可以扔掉重开。反过来把对话当记忆，等于把项目记在一个会失忆的人脑里。
3. **CLI 模式的价值是可控。** 命令行形态下，会话的开始结束、上下文的装载、每一步的命令和输出，都是明摆着的、可查的、可复现的。出了偏差能定位是哪一步开始偏的；图形界面里聊出来的偏差，往往查无实据。

## 怎么做

- **立断舍离的规矩**：一个话题聊了几轮还没收敛，或者开始出现前后矛盾，主动结束：把已定的结论、未决的问题、下一步，写成一段交接文字存进项目文件，新开会话时先喂这段交接。交接写得好，新会话三十秒进入状态。
- **每轮对话的产出要落盘**：定了的事进决策记录，状态变了更新项目档案，没落盘的结论一律视为没定——这句话要对自己狠：包括你自己在聊天里随口答应的。
- **长任务用 CLI 跑**：跨多文件、多步骤、要留痕的活，优先命令行形态；聊天框留给短问答和起草。工具形态要跟活的风险匹配，这也是混搭（入门版第 6 章）在工作方式上的延伸。

## 练一练

翻一个你最近聊得最久的会话：从里面找出三条已经拍板的结论，查一遍它们落盘了没有。再实际做一次交接演练：用十行字写清这个项目的现状和下一步，新开一个会话喂给它，看它能不能接得上。接不上，说明你的交接漏了关键项——漏的项，就是以后每次交接的必查项。

## 想深一点

这一章和第 5 章是亲戚：状态只有一个准地方，在「人机协作」里的版本就是「记忆只有一个准地方」。团队层面靠唯一清单，个人层面靠项目文件。还有一层：主动结束对话，对人也是一种纪律——它逼你在结束前把事情想清楚、写明白。很多项目不是死于做错，是死于一直聊、一直觉得「还在推进」，却从没把结论钉死过。

## 给 agent 的话（复制给你的 agent 加载）

- 对话中一旦形成拍板结论，立即提醒主人落盘（写进项目文件/决策记录），并给出建议存放位置；主人未落盘前，在后续对话中标注该结论为「未落盘」。
- 察觉上下文出现前后矛盾、或同一约束被反复确认时，主动提示：建议结束本会话，并先生成交接摘要（已定结论、未决问题、下一步）。
- 长任务执行时，每完成一个阶段就把进度和证据写入项目文件，不许只在对话里汇报。

## 本章小问题（答案见 `答案/强化版答案.md`）

1. （现实问题）跟 agent 聊到第二十轮，它给的方案跟第三轮定的方向明显对不上。你先怀疑什么？接下来三步做什么？
2. （思维训练）为什么说「主动结束对话」对人也是一种纪律？它逼人做对的那件事是什么？

> **给 agent 的自查题**：盘点主人当前进行中的长会话：哪几个已经超过十轮？里面有没有未落盘的拍板结论？列出来，逐条建议落盘位置，报给主人。

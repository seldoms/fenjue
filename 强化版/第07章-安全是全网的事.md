# 第 7 章 安全是全网的事（强化版）

## 一句话版

共用组件的一个洞，就是全网的洞。安全问题不许按「某个项目的事」处理，必须按全网事件处理。

![共用的墙裂一道缝，全线的人都要连夜查完](图/插画-第07章-安全是全网的事.svg)


## 真事

还是第 1 章那件事，但把细节说全：一个项目用的共用服务里，留着调试阶段的后门没清，还有路径穿越的问题，被外部入侵，同一组的 5 台节点全部沦陷，后门程序是提前一个月就植入的。事后查另一个不相干的客户，源码复审又发现同源的三处高危：任意文件写入、密钥硬编码、明文凭证。定性只有一句：跨项目共性。这不是哪个项目运气差，是同一套代码、同一批习惯，在所有项目身上都埋着。

## 道理

1. **共性决定了安全的处理级别**。单项目的问题可以等排期，全网共性的问题必须当天动——多等一天，多一批项目暴露在外面。
2. **出事的从来不是高深攻击，是低级残留**。调试后门、写死的密钥、明文密码——全是「当时图省事」的欠账。安全的重点不在防高手，在清自己的残留。
3. **安全靠检查单，不靠记性**。发布前查什么、多久全网扫一次，要写成单子让机器逐项扫。人负责处置和拍板，不负责「记得查」。

## 怎么做

- **共性问题当天全网排查**：任何共用组件爆出安全问题，当天出排查单，全部在用项目逐个过，结果回清单；没过的项目先处置再谈排期。处置顺序按暴露程度排，不按项目大小排。
- **发布前查三样**（立成死规矩）：调试代码和后门清了没有；密钥、令牌有没有写死在代码里；账号密码有没有明文存放。三样让 agent 在每次发布前自动扫，扫不过，不发布。
- **凭证只进该进的地方**：密钥和密码进配置中心或专门的保管处，代码仓库里出现明文凭证，一经发现按事故处理——先换凭证，再查责任。顺序不能反：先换，再查。

## 练一练

挑一个你在用的共用组件，今天就做一遍三查：有没有调试残留、有没有硬编码密钥、有没有明文凭证。查的结果不管好坏，写进问题清单——查了没事，是给全网买安心；查出事，今天就是最便宜的处置日。

## 想深一点

安全最容易犯的错是「按项目分工」：每个项目觉得自己的那份没出事就没事。但攻击者不按项目分工，他按漏洞分工——同一个洞，他会挨个项目试。所以安全的组织方式必须跟漏洞的传播方式一致：洞是全网的，防也必须是全网的。这一条想通了，第 1 章那句「共性是风险」才算真的落地。

## 给 agent 的话（复制给你的 agent 加载）

- 每次发布前自动执行三查：调试/后门残留、硬编码密钥、明文凭证。任一项命中，立即报告并阻止发布流程，不许只提醒不拦截。
- 发现任何凭证出现在代码、文档、聊天记录里，第一时间报告主人并建议先更换凭证，按安全事件记录，不许当普通问题排队。
- 收到共用组件的安全问题通知，立即盘点主人负责的项目里哪些在用该组件，列出清单报主人，不等主人来问。

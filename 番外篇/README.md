# 番外篇：好用的外部工具和 skill

> 这一篇在两版书的**外面**。书里讲的是道理和方法，这一讲的是家伙事儿：外面那些现成的 AI 工具、插件、skill，哪些真好用。它不由作者一个人写，由**每个读者把自己的实战经验登记上来**，全队一起验、一起维护。

## 为什么有这一篇

一个好工具被一个人发现，只值一个人的效率；被全队验过、登记在册，它就成了团队资产。更重要的是：**围绕同一个产品、同一类项目攒下来的工具经验，才是真正能流转的方法论**——道理在书里，家伙在这一篇，两样合起来，skill 才在团队里转得起来，而不是各人收藏夹里躺着。

## 收录门槛（先说死，免得变成广告墙）

**用过，不算数。** 一条工具想进这一篇，必须满足下面两条中的一条，并且带一个真案例：

1. **真用过，而且非常满意**——不是「还行」，是「下次碰到这类活，我第一个想起它」；
2. **极少的时间、或极少的问答轮次，就达到了满意的效果**——比如别人干半天的活，它三轮对话干完；一小时的活，它十分钟出活。

达不到这个门槛的，不许往上登。宁可这一篇长期只有十条真的，不堆一百条凑数的。

## 技巧攒在哪儿

很多工具，装上只是第一步，用得好不好全在几个窍门上。这类技巧在书里的安排是分工的：

- **正文各章里只提一句**：讲到哪类活、顺手点一句「有个窍门，见番外篇某条目」，点到为止，不在正文里展开写教程——正文是讲道理的，塞满操作细节，谁都读不下去。
- **技巧的正本攒在这一篇**：每个条目必填一句「使用技巧」，跟着条目一起被全队验证。谁在实战里试出新窍门，回来补进条目、在验证记录里留一行，技巧就这样一条条长起来，还自带真假检验。

一句话：道理在正文，窍门在番外，两边互相指路。

## 经验从哪来：翻你自己最近一个月的记录

每个人的聊天记录，就是自己没意识到的经验库。整理方法：

- 让你的 agent 把你**最近一个月**的 AI 对话记录过一遍，找出里面提到、用到的外部工具和 skill；
- 逐个对门槛：哪些你用完是真满意的？哪些是「没几轮就出活」的？
- 对得上的，按下面的模板写成案例——**只写自己的真事，不许听说、不许转述营销文案**；对不上的，一个字都不要写。

## 条目模板（每个工具一个文件，放 `番外篇/条目/` 下）

```
# 工具名

- 一句话：它干什么的
- 链接：官方地址
- 适用：哪类产品 / 哪类项目 / 哪种活
- 费用与门槛：免费 / 收费多少 / 要不要梯子或企业渠道

## 案例（必填，来自登记人本人）

- 什么活：
- 怎么用的（几步说清）：
- 花了多久 / 问了几轮：
- 效果如何（带数字更好）：
- 使用技巧（一两句）：这个工具最关键的窍门，别人照着能少走弯路的

## 全队验证

- 好用：0
- 不好用：0
- 验证记录：（谁、什么时候、在什么项目上试的、结论一句）
```

## 两个数字：好用 / 不好用

每条工具都挂着两个数，谁都能看见：

- 其他开发人员**亲自实践过**之后（不是看介绍觉得行），回来登记一票：好用，或者不好用；
- 两个数就写在条目里，也汇总在 `登记表.md` 上——挑工具的时候先看这两个数，再看案例；
- **不好用的票同样宝贵**：它告诉后面的人「这个活别用它」。票数攒多了不好用明显占上风的条目，维护者标「存疑」，再攒就下架讨论；
- 投票必须留名和场景（在什么项目、干什么活投的），匿名票、没试过的票，不算数。

## 维护规矩

- 提交方式和正文一样：走 PR、人是闸口（见仓库根目录 `共创机制.md`），脱敏红线同样适用——案例里不许出现客户真名、地址、账号、生产数据；
- 按**产品 / 项目类型**归类维护：同一类项目的工具经验放一起，后来人接同类项目，先翻这一篇的对应类目；
- 工具会变：条目超过三个月没人验证的，标「待复验」；验证过的，更新日期和两个数；
- 维护者（Luna）每周五随本书一起巡一遍：新条目合入后同步更新 `登记表.md`。

## 这一篇跟正文的关系

正文教你判断，这一篇帮你省下试错。顺序别反：先有判断（知道自己要什么活、什么算好），再挑工具；挑完工具用顺手了，把案例登回来——**你登的每一条，都是在给全队的方法论添一块能直接上手的部分。**
